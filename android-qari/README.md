# 📱 همیار قاری — اپ کاملاً بومی اندروید (Kotlin)

تحلیلگر گسترهٔ صدای خواننده: **بالاترین و پایین‌ترین نتی که خوانده شده**،
گستره بر حسب نیم‌پرده/اکتاو، نمودار «ردِّ صدا»، جدول سهم نت‌ها، مکث‌ها و
گزارش قابل‌ذخیره — همه روی خود گوشی.

> **این اپ هیچ WebView، هیچ HTML، هیچ سرور و هیچ مجوز اینترنتی ندارد.**
> Kotlin خالص + API های خود اندروید (MediaCodec، AudioRecord، Canvas، MediaStore).
> برای اثبات: بعد از نصب، حالت هواپیما را روشن کنید؛ همه‌چیز کار می‌کند.


اسکریپت هیچ merge و هیچ pull requestی نمی‌سازد، بازنویسیِ تاریخ را رد می‌کند

### موتور F0 نسخهٔ ۱٫۱٫۴ (تفکیک چهار مسئله)

موتور جدید همان قرارداد خروجی قبلی را حفظ می‌کند (`Report`، `PitchTrack`، JSON)
و چهار وظیفه را از هم جدا نگه می‌دارد:

| وظیفه | کجا | ورودی → خروجی |
|---|---|---|
| **A) اعتبار صوت** | `PitchEngine.frameConfidence` | ویژگی‌های یک فریم → `SILENT / INVALID / UNCERTAIN / VALID` |
| **B) تخمین F0** | `DualEstimator` | فریم صدا → چند نامزد F0 با امتیاز (YIN و MPM) |
| **C) ردیابی پیوسته** | `PitchEngine.track` | نامزدهای فریم‌ها → منحنی با پیوستگی زمانی |
| **D) تفسیر موسیقایی** | `Segmenter` + `Harmonics.refineNote` | منحنی معتبر → نت، گستره، فاصله |

اعتبارسنجی از ترکیب وزنیِ چند شاهد استفاده می‌کند و به آستانهٔ ثابت RMS یا
confidence تکیه نمی‌کند: نسبت به **کف نویز محلی** (صدک ۲۰٪ انرژی در بلوک‌های
۰٫۴ ثانیه‌ای، با ردیابی نویز متغیر)، **شفافیت تناوب** (YIN و MPM)، **توافق دو
تخمین‌گر**، **برجستگی هارمونیک‌ها نسبت به کف محلی طیف**، **سهم انرژی توضیح‌داده‌شده**،
**پخشی طیفی**، **شار طیفی** (شاهد نرم، تا تحریر واقعی حذف نشود) و **کلیپینگ**.
اگر دامنهٔ دینامیکی فایل کم باشد (صدای فشرده/AGC)، SNR قابل تخمین نیست و به‌جای
اینکه بهانهٔ رد کردن شود، از وزن آن کاسته می‌شود.

نکات پیاده‌سازی:

- **نامزدها به‌جای یک عدد**: هر فریم تا ۴ نامزد از دو تخمین‌گر (و فرض‌های ×۲/×۳
  برای دوره‌های روی‌شبکه‌ای) نگه می‌دارد؛ امتیاز هر نامزد از شواهد طیفی همان
  فریم می‌آید. ردیابی Viterbi با هزینهٔ گذارِ سقف‌دار انجام می‌شود، پس تغییر
  واقعی و سریع (تحریر) جریمهٔ نامتناهی نمی‌گیرد.
- **تحریر حفظ می‌شود**: هیچ صاف‌سازی تهاجمی روی منحنی نیست؛ فقط پرش‌های پرت
  (>۲۸۰ سنت از میانهٔ همسایگی، با وجود نامزد نزدیک‌تر) اصلاح می‌شوند.
  در بنچمارک، دامنهٔ ارتعاش خروجی/ورودی ۰٫۹۱–۰٫۹۴ است.
- **شکاف‌ها**: فقط شکاف‌های ≤۶۰ms که دو طرف و داخلشان شاهد اعتبار دارند با
  درون‌یابی پرشده و با `status = ESTIMATED` و `estimated = true` علامت می‌خورند.
  شکاف بلند هرگز پر نمی‌شود.
- **بدون حدس**: فریمی که اعتمادش کمتر از حدِ معتبر است، عدد تولید نمی‌کند
  (نه «نزدیک‌ترین نت حدسی»).
- **سازگاری**: `Analyzer.analyzeSignal(sig, denoise, progress, engine)` با
  `Engine.ENHANCED` (پیش‌فرض) یا `Engine.LEGACY` (مسیر قبلی). گزارش‌ها فیلدهای
  جدید `contourStatus`، `contourConfidence`، `validShare`، `uncertainShare`،
  `estimatedShare`، `engineName` را اضافه کرده‌اند و کلیدهای JSON قبلی
  دست‌نخورده مانده‌اند (`analysis` افزوده شده است).

**بازگشت به مسیر قبلی** (بدون حذف کد): کافی است در `analyzeSignal` مقدار
`engine` را `Engine.LEGACY` بدهید؛ مسیر YIN + `Harmonics.correctRuns` عیناً
دست‌نخورده باقی مانده است.

مراحل تحلیل (مسیر جدید):

1. یکسان‌سازی ورودی (همان قبلی): مونو، ۲۲٬۰۵۰ هرتز، حذف DC، بالاگذر ۴۵ هرتز،
   نرمال‌سازی پیک. نرمال‌سازی فقط برای پایداری عددی است، نه شاهد SNR.
2. تحلیل هر فریم: YIN و MPM روی یک FFT مشترک + ویژگی‌های طیفی + کف نویز محلی.
3. اعتبارسنجی فریم (چند شاهد، نه یک آستانه).
4. ردیابی نامزدها (Viterbi) + اصلاح پرش پرت + درون‌یابی شکاف کوتاه با علامت.
5. تفکیک نت‌ها و پالایش هر نت (همان مسیر قبلی) — کوانتیزه‌کردن نت جای دادهٔ خام
   F0 را نمی‌گیرد؛ منحنی خام در `contourT/contourHz` می‌ماند.

مراحل تحلیل (مسیر قبلی، برای مقایسه):

1. **یکسان‌سازی ورودی** — مونو، ۲۲٬۰۵۰ هرتز، حذف DC، بالاگذر ۴۵ هرتز،
   نرمال‌سازی پیک به ۰٫۹. یعنی mp3 و wav و ویدیو نتیجهٔ یکسان می‌دهند.
2. **ردیابی f0** با YIN (تابع تفاضل با FFT، O(N log N) — اجرای روی گوشی ممکن).
3. **اصلاح نردبان هارمونیک** — برای هر ران صدادار، فرض‌های ¼×، ⅓×، ½×، ۱×،
   ۲×، ۳×، ۴× با «امتیاز هماهنگی هارمونیک» سنجیده می‌شوند. این کار خطای اکتاو،
   خطای هارمونیک سوم/چهارم و گم‌شدن فرکانس پایه را می‌گیرد.
4. **پالایش هر نت** — طیف در طول نت میانگین گرفته می‌شود، جای هر هارمونیک با
   درون‌یابی سهمی پیدا و f0 با کمترین مربعات روی همهٔ هارمونیک‌ها برازش می‌شود.
5. **تفکیک نت‌ها** با هیسترزیس و ادغام شکاف‌های کوتاه؛ برای هر نت شفافیت،
   پایداری (سنت) و لغزش گزارش می‌شود.
6. **آمار گستره** روی نت‌های «واقعی» (۲ بار یا ≥۰٫۳ ثانیه)، و گزارش خام جداگانه.

۱۸ نمونهٔ مصنوعی با ground truth در سطح نمونه ساخته می‌شود (تلاوت تمیز، تحریر
سریع و پهن، بم ۹۲Hz، اوج ۶۲۰Hz، تغییر ناگهانی نت هر ۱۵۰ms، سکوت دیجیتال، هیس،

صوت+همهمه، بم با پایهٔ ضعیف، و نرخ‌های ۱۶k/۴۴٫۱k). معیارها: میانه/صدک۹۵ خطا
(سنت)، نرخ خطای اکتاو، نرخ خطای فاحش، نرخ رد اشتباه، نرخ پذیرش اشتباه در
سکوت/نویز/تشویق/همهمه، حفظ دامنهٔ تحریر، خطای شروع/پایان و زمان پردازش.
اگر نسخهٔ جدید در هر معیار بدتر شود، اسکریپت با کد غیرصفر خارج می‌شود.

### بازبینی مستقل: پوشش در برابر دقت (مرحلهٔ ۲)

یک ابزار بازبین جدا از بنچمارک اضافه شده است تا مطمئن شویم بهبود دقت از راه
«حذف فریم‌های سخت» به دست نیامده است:

```bash
# همان کلاس‌ها؛ فقط ابزار دیگری صدا زده می‌شود
java -cp /tmp/out:kotlin-stdlib.jar ir.hamyareqari.tools.PitchAudit --coverage
java -cp /tmp/out:kotlin-stdlib.jar ir.hamyareqari.tools.PitchAudit --mixture
java -cp /tmp/out:kotlin-stdlib.jar ir.hamyareqari.tools.PitchAudit --boundary
java -cp /tmp/out:kotlin-stdlib.jar ir.hamyareqari.tools.PitchAudit --tahrir
java -cp /tmp/out:kotlin-stdlib.jar ir.hamyareqari.tools.PitchAudit --memory --duration=1200
```

نتیجهٔ اندازه‌گیری‌شده (نمونه‌های مصنوعی):

| معیار | مسیر قبلی | موتور جدید |
|---|---|---|
| پوشش تجمعی فریم‌های واقعاً صدادار | ۱۰۰٪ (۱۴۸۵۷/۱۴۸۵۷) | **۹۹٫۹٪ (۱۴۸۳۵/۱۴۸۵۷)** |
| صدک۹۵ خطا با جریمهٔ فریم‌های ردشده | ۱۵۷ سنت (`steps_fast`) | **۴۰ سنت** |
| پذیرش اشتباه در گفتار یک‌نفره (بدون تلاوت) | ۶۸٫۹٪ / ۲۳ نت | ۵۸٫۹٪ / **۲۱ نت** |
| پذیرش اشتباه در همهمهٔ ۳ گوینده | ۹۶٫۳٪ | ۵۵٫۸٪ |
| تلاوت + همهمه در ‎+۶/۰/−۶‎ dB (میانهٔ خطا) | ۳٫۶ سنت | **۲٫۴ سنت** (پوشش ۱۰۰٪) |
| تلاوت + اکوی قوی (صدک۹۵) | ۱۲۰۱ سنت | **۲۸ سنت** |
| خطای مرز شروع/پایان (بدون ناحیهٔ کور) | ۲۱–۳۱ms | ۲–۲۶ms |
| سرباری حافظهٔ موتور (فایل ۲۰ دقیقه) | — | ۱۸MB (+۵۱MB خود PCM) |

**مسائل باز که در این مرحله فقط مستند شده‌اند (تغییر داده نشده‌اند):**

1. **گفتار یک‌نفره از تلاوت جدا نمی‌شود.** گفتار انسان هم تناوبی است؛ موتور آن
   را «معتبر» می‌شمارد (۵۸٫۹٪ فریم، ۲۱ نت از ۶ ثانیه). تفکیک قطعی گفتار از
   تلاوت با ویژگی‌های DSP ساده اثبات نشده است و ادعا نمی‌شود.
2. **لایهٔ استخراج نت با تحریر پهن مشکل دارد، نه منحنی F0.** آستانهٔ ادامهٔ
   ۷۲ سنت در `Segmenter` باعث می‌شود تحریر ±۱۷۰ سنتی به ۱۲۹ ران کوتاه بشکند و
   هیچ نتی تولید نشود؛ در تحریر ±۱۱۰ سنتی هم برعکس، ۶۲ نت کاذب ساخته می‌شود.
   منحنی F0 خام دست‌نخورده می‌ماند (اندازه‌گیری‌شده: آرایه پس از تفکیک نت
   بیت‌به‌بیت یکسان است) و حفظ دامنهٔ تحریر ۰٫۹۱–۰٫۹۴ است. اصلاح این لایه
   خروجی «نت/گستره/سهم/مکث» را در کل برنامه تغییر می‌دهد، پس به‌عنوان مسئلهٔ
   مستقل باقی مانده است.

**محدودیت صریح**: هیچ‌کدام از این اعداد روی «تلاوت واقعی قاریان با برچسب
متخصص» سنجیده نشده است. مجموعهٔ صوتی برچسب‌خوردهٔ مجاز در دسترس نبود؛ پس
بنچمارک فقط خطای نسبی دو مسیر و رگرسیون را ثابت می‌کند، نه دقت مطلق روی
تلاوت واقعی. آستانه‌ها با همین نمونه‌های مصنوعی تنظیم شده‌اند (نقطهٔ ضعف
روش) و باید با دادهٔ واقعی بازبینی شوند.

### اندازه‌گیری دقت (قابل تکرار)

```bash
cd android-qari
JAVA_HOME=... /path/to/java -cp kotlin-compiler.jar org.jetbrains.kotlin.cli.jvm.K2JVMCompiler \
  -no-reflect -jvm-target 1.8 -d /tmp/out src/ir/hamyareqari/dsp/*.kt tools/DspCheck.kt
java -cp /tmp/out:kotlin-stdlib.jar ir.hamyareqari.tools.DspCheck
```

یک اجرای مرجع (A3 → A4 و برگشت، ۱۴ نت، با ویبراتو و هارمونیک) در ۸ قالب سنجیده
می‌شود. نتیجهٔ آخرین اجرا:

| آزمون | بالاترین | پایین‌ترین | گستره | میانهٔ خطای کوک |
|---|---|---|---|---|
| مرجع ۲۲٬۰۵۰Hz | A4 | A3 | ۱۲٫۰۱ | ۱٫۰۵ سنت |
| نسخهٔ ۱۶٬۰۰۰Hz | A4 | A3 | ۱۲٫۰۱ | ۰٫۵۵ سنت |
| باند تلفنی ۸k | A4 | A3 | ۱۲٫۰۰ | ۰٫۵۱ سنت |
| کم‌صدا + نویز | A4 | A3 | ۱۲٫۰۱ | ۰٫۸۱ سنت |
| ۶۰ ثانیه سکوت در ابتدا | A4 | A3 | ۱۲٫۰۲ | ۱٫۰۴ سنت |
| نصف بلندی + قطبیت برعکس | A4 | A3 | ۱۲٫۰۱ | ۱٫۰۵ سنت |
| یک نت تنها C4 | C4 | C4 | ۰٫۰۰ | ۱٫۰۱ سنت |
| نت بم ۱۱۰Hz | A2 | A2 | ۰٫۰۰ | ۰٫۲۹ سنت |

روی تن خالص، خطا حدود **۰٫۱ سنت** است. آخرین اجرای بازبینی (پس از تغییر
لایهٔ اعتبارسنجی): همان ۸/۸ موفق، گسترهٔ ۱۱٫۹۸ نیم‌پرده و میانهٔ خطای
۰٫۹–۱٫۴ سنت، SNR ≈ ۲۸dB.

همان فایل نمونهٔ خود پروژه (`web/demo_bayati.wav`، تلاوت ۳۸٫۲۵ ثانیه‌ای) از مسیر

| | مرجع پروژه (وب) | اپ بومی (Kotlin) |
|---|---|---|
| بالاترین نت | A4 · ۴۴۰٫۴۱Hz | A4 · ۴۳۹٫۷۸Hz |
| پایین‌ترین نت | A3 · ۲۲۰٫۱۰Hz | A3 · ۲۱۹٫۸۵Hz |
| گستره | ۱۲٫۰۱ نیم‌پرده | ۱۲٫۰۰ نیم‌پرده |

یعنی دو پیاده‌سازی مستقل (JavaScript و Kotlin) روی دادهٔ واقعی به یک جواب

## ساخت دوباره از کد

بدون Gradle و بدون Android Studio (پس بدون دانلود چند صد مگابایتی):

```bash
bash android-qari/tools/fetch_toolchain.sh        # JDK + aapt2 + android.jar + d8 + kotlinc
ANDROID_TOOLS=/tmp/android bash android-qari/build_apk.sh
# خروجی: release/hamyar-qari-1.0.0.apk
```

ابزارها از npm و PyPI می‌آیند (نه از سرویس‌های تحریمی) و در `/tmp/android`
می‌نشینند؛ هیچ فایل باینری سنگینی داخل مخزن نمی‌ماند.

نسخهٔ بعدی:

```bash
VERSION_NAME=1.1.1 VERSION_CODE=3 bash android-qari/build_apk.sh
```

> ⚠️ برای به‌روزرسانی روی نسخهٔ نصب‌شده، باید همان کلید امضا بماند:
> `keystore/hamyar-qari.jks` (رمز `hamyarqari`). اگر این فایل را پاک کنید،
> کاربران باید اپ را حذف و دوباره نصب کنند.

## نکات صادقانه

- **رابط کاربری روی دستگاه واقعی اجرا نشده است.** هستهٔ تحلیل روی کامپیوتر با
  ۸ سناریو سنجیده شده، ولی صفحه‌ها، ضبط زنده و ذخیره‌سازی فقط از نظر کد
  بازبینی شده‌اند. دکمهٔ «آزمون داخلی موتور» برای همین گذاشته شده که با یک
  کلیک سلامت موتور را روی گوشی خودتان ببینید. اگر جایی خطا دید، بگویید تا
  دقیقاً همان را درست کنم.
- اپ عمداً **بدون مجوز اینترنت** ساخته شده؛ پس هیچ‌چیز نمی‌تواند جایی فرستاده شود.
- «بالاترین/پایین‌ترین نت» از نت‌های واقعاً خوانده‌شده گرفته می‌شود، نه از تک‌فریم‌ها.
- فایل‌های بلندتر از ۴۰ دقیقه فقط ۴۰ دقیقهٔ اول تحلیل می‌شوند (برای حافظه).
- پخش نمونه برای فایل‌های بیش از ۱۵ دقیقه خاموش است (نمودار و اعداد دست‌نخورده‌اند).
- تبدیل نرخ نمونهٔ رمزگشا با درون‌یابی خطی و بدون فیلتر ضدآلیاسینگ است؛ چون
  آلیاس در باند ۲–۱۱ کیلوهرتز می‌افتد، روی تشخیص f0 اثری ندارد.
- اپ برای یک کاربر طراحی شده؛ در حین تحلیل، رابط منتظر می‌ماند (تحلیل در
  ترد پس‌زمینه با نوار پیشرفت انجام می‌شود).
- **ویدیو**: کدگذار H.264 در حالت ByteBuffer (تبدیل ARGB→YUV420 در کد) استفاده
  می‌شود؛ روی همهٔ گوشی‌های اندروید ۸+ باید موجود باشد، ولی این مسیر روی
  دستگاه واقعی آزموده نشده. اگر دستگاه کدگذار AAC نداشت، ویدیو بی‌صدا ساخته
  می‌شود و همان را هم پیام می‌دهد. ۷۲۰p چند برابر ۵۴۰p طول می‌کشد.
- کاهش نویز برای فایل‌های تا ۲۵ دقیقه فعال است (بالاتر از آن، بی‌صدا و با
  هشدار، نادیده گرفته می‌شود).
- زوم نمودار در لحظهٔ جاری متمرکز می‌شود؛ اگر پخش متوقف باشد، وسط اجرا.
