# 🎚 ردِّ صدا — بالاترین و پایین‌ترین نتِ خوانده‌شده

تحلیلگر سبکِ صدا: فایل صوتی (تلاوت، آواز، تمرین) را می‌گیرد و به یک سؤال
ساده و دقیق جواب می‌دهد:

> **بالاترین نتی که خوانده شده چیست؟ پایین‌ترین نت کدام است؟ و صدا در این
> دو حد چه گستره‌ای (چند نیم‌پرده/اکتاو) را پوشش می‌دهد؟**

کنارش، یک نمایش بصری («ردِّ صدا») می‌سازد: خطوط نت + منحنی نرم صدا +
نقطهٔ نورانی متحرک که بین خطوط نت جابه‌جا می‌شود — هم به‌صورت PNG، هم
ویدیوی mp4 هم‌گام با صدا، هم به‌صورت زنده در مرورگر.

> این نسخه جای تحلیل مقام/سولفژ را گرفته است؛ تمام کد تشخیص مقام،
> سولفژ، امتیازدهی تمرین، یادگیری سبک و مقایسهٔ فراز از پروژه حذف شد.

> ## 🔒 پیش‌فرض: ۱۰۰٪ آفلاین — بدون سرور، بدون اینترنت
>
> کل تحلیل روی همان دستگاه انجام می‌شود (`web/engine.js` + `web/offline.js`):
> رمزگشایی فایل، استخراج F0، اصلاح اکتاو، تفکیک نت، ساخت PNG، ساخت ویدیو و
> «اجرای زنده». هیچ بایتی از صدای شما جایی فرستاده نمی‌شود و اپ بدون هیچ
> تنظیمی (بدون آدرس سرور) کار می‌کند. نسخهٔ سروری (FastAPI + Praat) هم در
> مخزن باقی است و فقط با `?engine=server` فعال می‌شود.

## قابلیت‌ها

| قابلیت | توضیح |
|---|---|
| 🎯 بالاترین/پایین‌ترین نت | از میان نت‌هایی که دست‌کم ۲ بار و در مجموع ≥۰٫۴٪ زمان خوانده‌شده اجرا شده‌اند (لغزش‌ها و نویز لحظه‌ای کنار گذاشته می‌شوند و جداگانه گزارش می‌شوند) |
| 📏 گسترهٔ صدا | نیم‌پرده، اکتاو و سنت بین بالاترین و پایین‌ترین نت + «مرکز صدا» |
| 🎼 نت‌به‌نت | زمان شروع، کشش، فرکانس، انحراف از کوک و پایداری هر نت |
| 📊 جدول سهم نت‌ها | کدام نت چقدر و چند بار خوانده شده |
| 🫁 نفس/مکث | تعداد سکوت‌های ≥۰٫۳ ثانیه + بلندترین مکث |
| 🎚 گستره به همهٔ واحدها | نیم‌پرده، پرده، اکتاو + باقی‌مانده، ربع‌پرده، درصد از یک اکتاو + نوار نقطه‌ای هر اکتاو |
| 🎬 ویدیوی نوار متحرک | پنجرهٔ لغزان (پیش‌فرض ۱۵s) یا همان قابی که خودت با دکمه‌های زوم انتخاب می‌کنی؛ نقطهٔ لحظهٔ جاری در وسط بوم |
| 🎯 فیلتر سخت‌گیرانهٔ نت‌ها | فقط نمونه‌های داخل نت‌های واقعی (≥۱۰۰ms، اتکا≥۰٫۳۵، فاصله ≤۹۰ سنت) رسم می‌شوند؛ میله‌های بلندِ بی‌نت حذف می‌شوند |
| 🎥 ورودی ویدیو | MP4/MOV (صدای AAC، با دمکس داخلی و WebCodecs) و هر فرمتی که مرورگر رمزگشایی می‌کند |
| 🖼 تصویر PNG | نمودار «ردِّ صدا» با سبک سرمه‌ای/طلایی |
| 🎬 ویدیوی mp4 | ۱۰۸۰p (یا ۷۲۰p با انتخاب خودت) · ۶۰fps؛ رندر آفلاین با **WebCodecs + mp4-muxer** (چند ثانیه برای چند دقیقه صدا، هم‌زمانی دقیق صوت/تصویر). اگر دستگاه WebCodecs/AAC نداشت، خودکار به مسیر قدیمی MediaRecorder برمی‌گردد |
| 🔍 زوم ردِّ صدا | ⏱ پنجرهٔ زمانی (کل اجرا … ۳s) و ↕ زوم ارتفاع (×۱ … ×۳٫۵)؛ همان تنظیم‌ها به ویدیو هم اعمال می‌شوند |
| 💾 ذخیرهٔ آفلاین | دکمه‌های «فایل اصلی / تصویر تحلیل / ویدیو / گزارش JSON» — با نام اصلی فایل |
| ▶️ پخش تعاملی | روی نمودار (یا لمس روی موبایل) → پخش از همان لحظه؛ منحنی و نقطه هم‌زمان حرکت می‌کنند |
| ⏺ اجرا با ضبط | میکروفون → نمایش زندهٔ نت + ضبط صدا در حافظه؛ در پایان تحلیل خودکار (نت‌ها/گستره/تصویر) و امکان ذخیرهٔ صدا، تصویر و گزارش برای هر ضبط |
| 🗑 حذف جلسه | حذف هر ضبط (با تأیید دو مرحله‌ای) و «حذف همه» برای پاک کردن کل جلسه |
| 📱 موبایل‌فرست | چیدمان تک‌ستونه، دکمه‌های ≥۴۶px، نوار تب چسبان، نمودارهای DPR-aware و خوانا روی گوشی |
| 📲 نصب‌پذیر (PWA) | مانیفست + آیکون‌های maskable + Service Worker برای باز شدن آفلاین پوستهٔ UI — پایهٔ ساخت APK |

### موتور آفلاین چگونه همان دقت را می‌دهد؟

نسخهٔ آفلاین، همان الگوریتم‌ها را با همان ثابت‌ها پیاده کرده است:

| لایه | سروری (پایتون) | آفلاین (جاوااسکریپت) |
|---|---|---|
| F0 | Praat `to_pitch_ac(very_accurate)` | خودهمبستگی نرمال‌شدهٔ پنجره‌ای (Boersma‑style) با پنجرهٔ ۳ دوره، گام ۵ms، آستانهٔ صداداری ۰٫۴۲، درون‌یابی سهمی |
| اصلاح خطای اکتاو/پنجم | نردبان هارمونیک فریم‌به‌فریم | همان (FFT، نسبت‌های ¼…۴، قاعدهٔ «پایین‌ترین فرضِ هم‌امتیاز») |
| موتور دوم | pYIN (librosa) | YIN با CMND (فقط برای هم‌رأیی/اطمینان) |
| تفکیک نت | هیسترزیس + ادغام | همان (آستانهٔ شروع ۴۵ سنت، ادامه ۷۲ سنت) |
| پالایش هر نت | برازش هارمونیک روی طیف ۱۶k | همان (FFT 16384 + درون‌یابی سهمی + کمترین مربعات) |
| گزارش/کیفیت | `range_analyzer.py` | همان ساختار JSON و همان آستانه‌های کیفیت |

**سنجش هم‌خوانی (همان اجرای مصنوعی، دو موتور):**

| نسخهٔ ورودی | سروری (python/Praat) | آفلاین (JS) | اختلاف |

| clean ۴۴٫۱k | E4/A3 · ۶٫۹۵ نیم‌پرده · ۱۴ نت | E4/A3 · ۶٫۹۴ · ۱۴ نت | ≤۰٫۵ سنت |
| ۸k | E4/A3 · ۶٫۹۵ | E4/A3 · ۶٫۹۴ | ≤۰٫۵ سنت |
| نویزی | E4/A3 · ۶٫۹۴ | E4/A3 · ۶٫۹۲ | ≤۱٫۵ سنت |
| باند تلفنی | E4/A3 · ۶٫۹۵ | E4/A3 · ۶٫۹۴ | ≤۰٫۵ سنت |
| کلیپ‌شده | E4/A3 · ۶٫۹۵ | E4/A3 · ۶٫۹۴ | ≤۰٫۸ سنت |

## ⚡ سرعت: پردازش موازی و جریانی

تحلیل بین چند Worker پخش می‌شود و در همان حال قطعه‌قطعه (جریانی) اجرا
می‌شود؛ پس حافظه ثابت می‌ماند و درصد پیشرفت همیشه تازه است.

| بخش | چه می‌کند |
|---|---|
| `web/parallel.js` | استخر تا **۴ کارگر** (`navigator.hardwareConcurrency`)، توزیع متعادل کارها، پیشرفت تجمیعی |
| `web/worker.js` | همان `engine.js` را بار می‌کند و فقط تکهٔ محاسبه را برمی‌گرداند (هیچ تصمیمی نمی‌گیرد) |
| برش صدا | هر کارگر فقط بازهٔ نمونه‌های همان تکه را می‌گیرد، نه کل فایل (مهم برای فایل بلند) |
| بازگشت امن | اگر Worker نباشد/خطا بدهد ⇒ بی‌صدا همان مسیر سریال؛ **نتیجه یکسان** |
| بهینه‌سازی تک‌هسته | FFT حقیقی (نصف کارِ FFT مختلط)، جدول چرخش کش‌شده، صفر تخصیص در حلقهٔ فریم‌ها |

**اندازه‌گیری واقعی** (۶۰ ثانیه صدا، یک هستهٔ Xeon، Node):

| نسخه | زمان | نسبت |
|---|---|---|
| قبل (۱٫۱٫۰) | ۴٫۹۵ ثانیه | — |
| ۱٫۲٫۰ سریال | ۲٫۲۴ ثانیه | **۲٫۲×** |
| ۱٫۲٫۰ موازی (۲ رشته) | ۱٫۸۱ ثانیه | **۲٫۷×** |

روی گوشی چند‌هسته‌ای، بخش‌های سنگین (`pitch` و `refine` که ۹۰٪ زمان‌اند) بین
هسته‌ها پخش می‌شوند؛ با ۴ هسته در عمل حدود **۴٫۵–۵ برابر** نسخهٔ ۱٫۱٫۰
می‌شود. عدد دقیق در فیلد `quality.parallel_cores` گزارش می‌شود.

## 🎙 اجرای زنده: بدون پرش، بدون نت جعلی

مشکل قبلی: «وقتی چیزی نمی‌خوانم، اپ خودش نت بالا و پایین می‌کند.» حالا سه
دروازهٔ مستقل جلوی این را می‌گیرند:

| لایه | کار |
|---|---|
| دروازهٔ بلندی | اگر rms زیر کفِ نویزِ یادگرفته‌شده باشد ⇒ «سکوت» (نه نت) |
| بالاگذر ۷۵ هرتز | هام برق، رامبل و لرزش میز از ورودی زنده حذف می‌شود |
| آستانهٔ دوره‌ای‌بودن | `strength ≥ ۰٫۵۵` و پوشش ≥ ۲٫۵ دورهٔ f0 |
| رد پیک لبه | اگر بهترین تأخیر روی لبهٔ بازهٔ جست‌وجو بیفتد (نشانهٔ هام/نویز) ⇒ بی‌نت |
| میانهٔ زمانی + رد پرش اکتاو | یک بستهٔ خطا نمایش را جابه‌جا نمی‌کند |
| پایداری ۳ بسته‌ای (≈۰٫۳۶ ث) | نت فقط وقتی نمایش داده می‌شود که «مانده» باشد |
| مهلت ۰٫۳ ثانیه | بعد از قطع صدا، نت قبلی کوتاه نگه داشته می‌شود، بعد صفحه «—» می‌شود |

**نمایش نرم:** رسم در حلقهٔ `requestAnimationFrame` (۳۰ فریم بر ثانیه) با
میان‌یابی نمایی انجام می‌شود — نقطه روی خطوط نت می‌لغزد، نمی‌پرد. متن‌ها فقط
با تغییر واقعیِ نت عوض می‌شوند تا چیدمان صفحه نلرزد. هزینهٔ تحلیل هر بستهٔ
۱۲۰ میلی‌ثانیه‌ای ≈ **۲٫۵ میلی‌ثانیه** است (۴۷ برابر سریع‌تر از بیدرنگ).

## یک نتیجه برای هر اجرا (استانداردسازی ورودی)

مشکل قدیمی: «با بعضی آپلودها درست است و با بعضی نه». ریشه‌اش این بود که
هر فایل، دست‌نخورده به موتور می‌رفت؛ نرخ نمونه، تعداد کانال، بلندی و
فرمت روی نتیجه اثر می‌گذاشت. حالا **همهٔ ورودی‌ها از یک درِ ورودی یکسان**
عبور می‌کنند (`analysis_engine.prepare_audio`) و به یک «مبنای ثابت»
می‌رسند:

| مرحله | کار |
|---|---|
| رمزگشایی | ffmpeg جریانی (صدا یا صدای ویدیو) → WAV شناور |
| مونو | میانگین کانال‌ها، ولی اگر کانال‌ها **فازمخالف** باشند کانال قوی‌تر (جلوگیری از حذف صدا) |
| نرخ نمونه | همیشه ۲۲٬۰۵۰ هرتز (soxr/ffmpeg) |
| DC و رامبل | حذف میانگین + بالاگذر ۴۵ هرتز |
| بلندی | نرمال‌سازی پیک به ۰٫۹ |
| پردازش | بلوکی (حافظهٔ ثابت؛ فایل ۴۶ دقیقه‌ای هم امن است) |

و بعد از استخراج F0 با Praat:

* **اصلاح «نردبان هارمونیک»**: برای هر ران صدادار، فرض‌های `f×(¼, ⅓, ½, ۱, ۲, ۳, ۴)`
  با «امتیاز هماهنگی هارمونیک» سنجیده می‌شوند — فریمی که فاقد هارمونیک‌های
  فردِ فرض باشد جریمه می‌شود. این کار هم خطای اکتاو (۲×)، هم خطای
  هارمونیک سوم/چهارم (۳×، ۴×) و هم **گم‌شدن فرکانس پایه** (بلندگوی گوشی،
  باند تلفنی، صدای سینه‌ای ضعیف) را ریشه‌ای می‌گیرد. امتیازدهی
  **فریم‌به‌فریم** است، پس ویبراتو و گلیساندو نتیجه را خراب نمی‌کنند.
* **هم‌سنجی با pYIN**: موتور دوم مستقل؛ فقط برای گزارش «هم‌رأیی» و
  «اطمینان» استفاده می‌شود و **منحنی F0 را تغییر نمی‌دهد** (اگر تغییر
  می‌داد، نتیجه به اجرا‌شدنِ pYIN — و بنابراین به طول فایل — وابسته می‌شد).
* **پالایش هر نت با برازش هارمونیک**: جای هر هارمونیک در طیف با درون‌یابی
  سهمی پیدا و f0 با کمترین مربعات روی همهٔ هارمونیک‌ها برازش می‌شود.
  دقت روی تن خالص زیر **۰٫۱ سنت** است (پیش‌تر با میانگین‌گیری فریم‌ها
  چند سنت بود). این مرحله «پشتیبانی هارمونیک» هر نت را هم می‌سنجد تا
  نویز/نت شبح‌وار نتواند بالاترین یا پایین‌ترین نت را تعیین کند.
* **گام زمانی ثابت ۵ میلی‌ثانیه** برای همهٔ فایل‌ها و **بازهٔ جست‌وجوی
  ثابت ۵۵–۱۲۰۰ هرتز**؛ قبلاً گام زمانی به طول فایل بسته بود و همان اجرا
  با ۶۰ ثانیه سکوتِ اضافه در ابتدا، نتیجهٔ دیگری می‌داد.
* **تفکیک نت با هیسترزیس**: آستانهٔ شروع ۴۵ سنت و ادامه ۷۲ سنت، ادغام
  شکاف‌های کوتاه، و برای هر نت «اطمینان» و «پایداری» گزارش می‌شود.

باند تلفنی، هام ۵۰ هرتز و هیس. خروجی فعلی: **۱۰۰٪ نت‌های درست،
میانهٔ خطای کوک ۰٫۹–۱٫۴ سنت، پراکندگی بین نسخه‌ها ≤ ۱٫۴ سنت**.

سپس همان اجرا با تغییرهای «بی‌ربط» دوباره تحلیل می‌شود — ۲ ثانیه و ۶۰
ثانیه سکوت در ابتدا، نصفِ بلندی، قطبیت برعکس — و باید **عدد یکسان**
بدهد: اختلاف فعلی **۰٫۰۰ سنت** و تعداد نت یکسان.

```js

LocalOffline.jobs, LocalOffline.fetch, LocalOffline.WebSocket  // جایگزین‌های محلی
```

## ذخیرهٔ ویدیو در گالری

ویدیو با دکمهٔ «🎬 ساخت ویدیوی ردِّ صدا» ساخته می‌شود.

**سرعت:** تا پیش از ۱٫۳٫۰ ویدیو هم‌زمان با پخش صدا ضبط می‌شد، پس یک فایل
۳ دقیقه‌ای ۳ دقیقه طول می‌کشید. از ۱٫۳٫۰ فریم‌ها **آفلاین** رسم و با
WebCodecs کدگذاری می‌شوند: هر فریم برچسب زمانی دقیق `i/fps` می‌گیرد (بدون
تأخیر صوت/تصویر) و کل ویدیو در چند ثانیه آماده می‌شود. برای فایل‌های بلند،
نرخ بیت/فریم خودکار کم می‌شود تا حافظه پر نشود.

**ظاهر:** نمودار اپ، تصویر PNG و ویدیو همه از یک فایل رسم می‌کنند
(`web/trace_style.js`) — همان نقطهٔ نورانی، هاله، خط پخش، رنگ‌ها و برچسب‌ها.
تست `trace_style_test` نشان می‌دهد خروجی اپ و ویدیو **پیکسل‌به‌پیکسل** یکی است
(اختلاف ۰٫۰۰px).

بعد از ساخت، ویدیو دو مسیر دارد:

| مسیر | چه می‌کند |
|---|---|
| **📥 ذخیرهٔ ویدیو در گالری** | بلاب محلی ویدیو را با پل بومی در `Movies/` می‌نویسد (در مرورگر: `navigator.share`) |
| **🎬 فایل ویدیو** | دانلود مستقیم ویدیو با نام `‹نام فایل شما›-radde-seda.mp4` (یا `.webm` اگر مرورگر mp4 ندهد) |

اگر مرورگر Web Share سطح ۲ را پشتیبانی نکند، همان دکمه خودکار به دانلود
ساده برمی‌گردد تا هیچ‌وقت دست خالی نمانی.

## نکات صادقانه

- «بالاترین/پایین‌ترین نت» از **نت‌های واقعاً خوانده‌شده** گرفته می‌شود
  (حداقل ۲ بار و به‌اندازهٔ کافی طولانی)؛ جیغ‌های لحظه‌ای، لغزش‌ها و خطاهای
  تک‌اکتاوی Praat در گستره شمرده نمی‌شوند و در فیلدهای `raw_highest` /
  `raw_lowest` جداگانه گزارش می‌شوند. مثال واقعی روی یک تلاوت ۴۶ دقیقه‌ای:
  خام G5/C#2 (۰٫۲ و ۰٫۳ ثانیه) اما گسترهٔ واقعی A#2 ↔ C5 (۲٫۲ اکتاو).
- اگر خواندن با ویبراتوی شدید همراه باشد، نت همچنان یک نت شمرده می‌شود
  (پایداری هر نت در خروجی گزارش شده است).

### دربارهٔ «۱۰۰٪ آفلاین» — شفاف و بی‌اغراق

| موضوع | وضعیت |
|---|---|
| صدا و تصویر شما | هرگز از دستگاه بیرون نمی‌رود؛ هیچ درخواست شبکه‌ای در حالت آفلاین زده نمی‌شود (در تست خودکار شمرده شده: **صفر**) |
| موتور تحلیل | خودهمبستگی نرمال (هم‌خانوادهٔ Praat) + اصلاح نردبان هارمونیک + موتور دوم YIN؛ اختلاف با نسخهٔ Praat-server زیر **۱٫۵ سنت** |
| MP3 / WAV / OGG / FLAC / M4A | رمزگشایی با `AudioContext.decodeAudioData` خود مرورگر/WebView |
| MP4 / MOV (ویدیو) | دمکس داخلی + `AudioDecoder` (WebCodecs). **اگر WebView گوشی WebCodecs نداشته باشد**، پیام فارسی روشن نشان داده می‌شود و توصیه می‌کند صدا را جدا کنید — این تنها نقطهٔ وابسته به نسخهٔ WebView است |
| ویدیوی خروجی | `MediaRecorder`؛ mp4 اگر پشتیبانی شود، وگرنه webm (هر دو در گالری/پخش‌کننده باز می‌شوند) |
| اجرای زنده | میکروفون → تحلیل در همان صفحه؛ هیچ سوکتی باز نمی‌شود |
| PWA | بعد از اولین بارگذاری، پوسته از Service Worker (`radde-seda-shell-v8`) می‌آید و اپ بدون اینترنت باز می‌شود |

آنچه آفلاین **نیست** و به‌عمد حذف شده: هیچ. تنها وابستگی، خودِ مرورگر/WebView
است؛ نه سرور، نه ffmpeg، نه Praat، نه اینترنت.

- **موازی‌سازی فقط سرعت را عوض می‌کند، نه نتیجه را.** تست خودکار
  (`web/tests/parallel_test.js`) گزارش مسیر موازی و سریال را بیت‌به‌بیت
  مقایسه می‌کند و اگر Worker در دسترس نباشد/خطا بدهد، موتور خودش به مسیر
  سریال برمی‌گردد.
- اعداد سرعت روی یک هستهٔ Xeonِ این محیط گرفته شده (۲ رشته، ۱ هستهٔ فیزیکی).
  روی گوشی، هم مطلق کندتر است و هم موازی‌سازی بیشتر به کار می‌آید:
  با ۴ هسته انتظار **۴٫۵–۵ برابر** نسخهٔ ۱٫۱٫۰ را داریم. پیشرفت زنده و
  نشان «⚡ N هسته» بالای نوار پیشرفت نشان می‌دهد کدام مسیر فعال است.
- تشکیل استخر کارگر خودش ~۱۰۰ میلی‌ثانیه اول کار دارد؛ برای فایل‌های خیلی
  کوتاه (زیر ۳ ثانیه) ممکن است موازی سود چندانی نداشته باشد.
- حالت `?engine=server` قدیمی است و برای دمو/توسعه نگه داشته شده: بدون
  احراز هویت و rate-limit. اگر آن را عمومی منتشر می‌کنید این‌ها را اضافه کنید.
- در «اجرای زنده» نت‌های زیر ~۷۸ هرتز (هام برق/رامبل) عمداً نادیده گرفته
  می‌شوند؛ اگر روزی نیاز به تحلیل باسِ خیلی پایین داشتید، `hiPassHz` را در
  `extractPitchChunkInfo` پایین بیاورید.
