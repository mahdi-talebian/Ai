# 🎚 ردِّ صدا — بالاترین و پایین‌ترین نتِ خوانده‌شده

تحلیلگر سبکِ صدا: فایل صوتی (تلاوت، آواز، تمرین) را می‌گیرد و به یک سؤال
ساده و دقیق جواب می‌دهد:

> **بالاترین نتی که خوانده شده چیست؟ پایین‌ترین نت کدام است؟ و صدا در این
> دو حد چه گستره‌ای (چند نیم‌پرده/اکتاو) را پوشش می‌دهد؟**

کنارش، یک نمایش بصری («ردِّ صدا») می‌سازد: خطوط نت + منحنی نرم صدا +
نقطهٔ نورانی متحرک که بین خطوط نت جابه‌جا می‌شود — هم به‌صورت PNG، هم
ویدیوی mp4 هم‌گام با صدا، هم به‌صورت زنده در مرورگر.

> این نسخه جای تحلیل مقام/سولفژ را گرفته است؛ تمام کد تشخیص مقام،
> سولفژ، امتیازدهی تمرین، یادگیری سبک و مقایسهٔ فراز از پروژه حذف شد.

## معماری

```

server/main.py              FastAPI: آپلود، تحلیل، ویدیو، وضعیت، فایل، WebSocket
python/range_analyzer.py    گزارش دامنهٔ صدا (گزارش JSON + PNG) — لایهٔ دامنه/اکتاو
python/analysis_engine.py   موتور تحلیل: استانداردسازی + Praat + اصلاح نردبان
                            هارمونیک + هم‌سنجی pYIN + تفکیک نت + کیفیت
python/trace_video.py       رندر «ردِّ صدا» (PNG/MP4)
python/pitch_engine.py      توابع پایه: تبدیل فرکانس↔نت، هموارسازی، تفکیک نت
python/tests/test_accuracy.py  بنچمارک «هم‌خوانی و دقت نت» (۱۳ نسخهٔ ورودی)
```

### چرا Praat؟

استخراج فرکانس پایه با `to_pitch_ac(very_accurate=True)` و پاس دوگانهٔ
پالایش انجام می‌شود؛ روی تن خالص و ربع‌پرده‌ای خطای نزدیک صفر سنت دارد
(در مقابل ~۷ سنت خطای pYIN) — یعنی تشخیص «A3» یا «A4» بودن نت با اطمینان
بالا انجام می‌شود. برای فایل‌های بلند، پردازش **پنجره‌ای** است تا حافظه
سرریز نکند.

## یک نتیجه برای هر اجرا (استانداردسازی ورودی)

مشکل قدیمی: «با بعضی آپلودها درست است و با بعضی نه». ریشه‌اش این بود که
هر فایل، دست‌نخورده به موتور می‌رفت؛ نرخ نمونه، تعداد کانال، بلندی و
فرمت روی نتیجه اثر می‌گذاشت. حالا **همهٔ ورودی‌ها از یک درِ ورودی یکسان**
عبور می‌کنند (`analysis_engine.prepare_audio`) و به یک «مبنای ثابت»
می‌رسند:

| مرحله | کار |
|---|---|
| رمزگشایی | ffmpeg جریانی (صدا یا صدای ویدیو) → WAV شناور |
| مونو | میانگین کانال‌ها، ولی اگر کانال‌ها **فازمخالف** باشند کانال قوی‌تر (جلوگیری از حذف صدا) |
| نرخ نمونه | همیشه ۲۲٬۰۵۰ هرتز (soxr/ffmpeg) |
| DC و رامبل | حذف میانگین + بالاگذر ۴۵ هرتز |
| بلندی | نرمال‌سازی پیک به ۰٫۹ |
| پردازش | بلوکی (حافظهٔ ثابت؛ فایل ۴۶ دقیقه‌ای هم امن است) |

و بعد از استخراج F0 با Praat:

* **اصلاح «نردبان هارمونیک»**: برای هر ران صدادار، فرض‌های `f×(¼, ⅓, ½, ۱, ۲, ۳, ۴)`
  با «امتیاز هماهنگی هارمونیک» سنجیده می‌شوند — فریمی که فاقد هارمونیک‌های
  فردِ فرض باشد جریمه می‌شود. این کار هم خطای اکتاو (۲×)، هم خطای
  هارمونیک سوم/چهارم (۳×، ۴×) و هم **گم‌شدن فرکانس پایه** (بلندگوی گوشی،
  باند تلفنی، صدای سینه‌ای ضعیف) را ریشه‌ای می‌گیرد. امتیازدهی
  **فریم‌به‌فریم** است، پس ویبراتو و گلیساندو نتیجه را خراب نمی‌کنند.
* **هم‌سنجی با pYIN**: موتور دوم مستقل؛ فقط برای گزارش «هم‌رأیی» و
  «اطمینان» استفاده می‌شود و **منحنی F0 را تغییر نمی‌دهد** (اگر تغییر
  می‌داد، نتیجه به اجرا‌شدنِ pYIN — و بنابراین به طول فایل — وابسته می‌شد).
* **پالایش هر نت با برازش هارمونیک**: جای هر هارمونیک در طیف با درون‌یابی
  سهمی پیدا و f0 با کمترین مربعات روی همهٔ هارمونیک‌ها برازش می‌شود.
  دقت روی تن خالص زیر **۰٫۱ سنت** است (پیش‌تر با میانگین‌گیری فریم‌ها
  چند سنت بود). این مرحله «پشتیبانی هارمونیک» هر نت را هم می‌سنجد تا
  نویز/نت شبح‌وار نتواند بالاترین یا پایین‌ترین نت را تعیین کند.
* **گام زمانی ثابت ۵ میلی‌ثانیه** برای همهٔ فایل‌ها و **بازهٔ جست‌وجوی
  ثابت ۵۵–۱۲۰۰ هرتز**؛ قبلاً گام زمانی به طول فایل بسته بود و همان اجرا
  با ۶۰ ثانیه سکوتِ اضافه در ابتدا، نتیجهٔ دیگری می‌داد.
* **تفکیک نت با هیسترزیس**: آستانهٔ شروع ۴۵ سنت و ادامه ۷۲ سنت، ادغام
  شکاف‌های کوتاه، و برای هر نت «اطمینان» و «پایداری» گزارش می‌شود.

### بنچمارک دقت (قابل تکرار)

```bash
cd python && python3 tests/test_accuracy.py
```

یک اجرای مرجع مصنوعی (۱۴ نت، A3↔A4، با ویبراتو/جیتر/فرم‌انت) ساخته
می‌شود و همان اجرا در ۱۳ قالب بررسی می‌شود: ۴۴٫۱k/۱۶k/۴۸k/۸k، MP3،
استریوی فازمخالف، ۳۸‑دسی‌بل کم‌صدا، نویزی، رامبل ۴۲ هرتز، کلیپ‌شده،
باند تلفنی، هام ۵۰ هرتز و هیس. خروجی فعلی: **۱۰۰٪ نت‌های درست،
میانهٔ خطای کوک ۰٫۹–۱٫۴ سنت، پراکندگی بین نسخه‌ها ≤ ۱٫۴ سنت**.

سپس همان اجرا با تغییرهای «بی‌ربط» دوباره تحلیل می‌شود — ۲ ثانیه و ۶۰
ثانیه سکوت در ابتدا، نصفِ بلندی، قطبیت برعکس — و باید **عدد یکسان**
بدهد: اختلاف فعلی **۰٫۰۰ سنت** و تعداد نت یکسان.

## API

| مسیر | توضیح |
|---|---|
| `POST /api/upload` | آپلود فایل صوتی/ویدیویی → `job_id` (+ نام اصلی و `kind`) |
| `POST /api/analyze/{job_id}` | شروع تحلیل (`denoise` اختیاری)؛ گزارش JSON |
| `POST /api/video/{job_id}` | ساخت ویدیو با `fps` (پیش‌فرض ۲۰) |
| `GET /api/status/{job_id}` | وضعیت/پیشرفت/نتیجه |
| `GET /api/file/{job_id}/{name}` | دسترسی به فایل‌های خروجی (پخش در صفحه) |
| `GET /api/download/{job_id}/{kind}` | **ذخیره روی دستگاه**: `original` (فایل آپلودی با نام اصلی) · `image` · `report` · `video` |
| `GET /api/health` | سلامت سرور |

هر گزارش یک بخش `quality` دارد (وضعیت `excellent/good/fair/poor`، هشدارهای
فارسی، درصد هم‌رأیی دو موتور، میانگین اطمینان نت‌ها، نرخ نمونهٔ ورودی و
شمار اصلاح‌های نردبان هارمونیک) که در رابط کاربری به شکل نشان کیفیت
نمایش داده می‌شود.
| `WS /ws/job/{job_id}` | پیشرفت زندهٔ تحلیل/رندر |
| `WS /ws/live-pitch` | استریم PCM میکروفون → نت + رکورد جلسه |

## اجرای زنده: دو حالت (طبق نیاز کاربر)

| حالت | صدا | نتیجه در حافظه |
|---|---|---|
| ⚡ **لحظه‌ای** | فقط تحلیل می‌شود و دور ریخته می‌شود | هیچ چیز نمی‌ماند؛ با توقف، نت‌ها/رکورد/نمودار پاک می‌شوند |
| ⏺ **با ضبط** | در حافظهٔ مرورگر ضبط می‌شود (WAV ۱۶ بیت) | هر ضبط یک ردیف در «ضبط‌های این جلسه» می‌شود: پخش، ذخیرهٔ صدا، تحلیل کامل، تصویر و گزارش |

ضبط با `ScriptProcessor` انجام می‌شود (نه `MediaRecorder`) تا در WebView اندروید هم
قابل اعتماد باشد و خروجی مستقیماً WAV قابل تحلیل باشد.

## موبایل و مسیر رسیدن به APK اندروید

رابط از ابتدا موبایل‌فرست نوشته شده (یک‌ستونه، دکمه‌های بزرگ، نوار تب چسبان،
نمودار با مقیاس `devicePixelRatio`) و فونت محلی `Estedad` دارد.

آماده‌های نصب به‌عنوان اپ (PWA):

- `web/manifest.webmanifest` — نام، آیکون‌ها (شامل maskable)، `display: standalone`
- `web/sw.js` — کش پوستهٔ UI (HTML/فونت/آیکون) برای باز شدن آفلاین
- `web/icons/*` — آیکون‌های ۱۹۲/۵۱۲/ماسکبل/اپل

برای ساخت APK بعداً دو مسیر ساده:

1. **Bubblewrap / PWABuilder** — همین PWA را در یک Trusted Web Activity می‌پیچد.
2. **Capacitor** — `web/` را داخل WebView می‌گذارد و با پلاگین‌هایی مثل
   `@capacitor/filesystem` می‌توان ذخیرهٔ فایل‌ها را بومی کرد.

نکتهٔ مهم: در APK، صفحه از `https://localhost` سرو می‌شود و باید آدرس سرور
تحلیل را بدهید. این کار از قبل پیش‌بینی شده است:

```
?api=https://your-server.example      # یا: localStorage.setItem('api_base', '...')
```

همهٔ درخواست‌ها و WebSocketها (پیشرفت تحلیل و پیانوی زنده) از همان مقدار پیروی می‌کنند.

ویدیو با دکمهٔ «🎬 ساخت ویدیوی ردِّ صدا» ساخته می‌شود و بعد از آن دو مسیر دارد:

| مسیر | چه می‌کند |
|---|---|

اگر مرورگر Web Share سطح ۲ را پشتیبانی نکند، همان دکمه خودکار به دانلود
ساده برمی‌گردد تا هیچ‌وقت دست خالی نمانی.

## نکات صادقانه

- «بالاترین/پایین‌ترین نت» از **نت‌های واقعاً خوانده‌شده** گرفته می‌شود
  (حداقل ۲ بار و به‌اندازهٔ کافی طولانی)؛ جیغ‌های لحظه‌ای، لغزش‌ها و خطاهای
  تک‌اکتاوی Praat در گستره شمرده نمی‌شوند و در فیلدهای `raw_highest` /
  `raw_lowest` جداگانه گزارش می‌شوند. مثال واقعی روی یک تلاوت ۴۶ دقیقه‌ای:
  خام G5/C#2 (۰٫۲ و ۰٫۳ ثانیه) اما گسترهٔ واقعی A#2 ↔ C5 (۲٫۲ اکتاو).
- اگر خواندن با ویبراتوی شدید همراه باشد، نت همچنان یک نت شمرده می‌شود
  (پایداری هر نت در خروجی گزارش شده است).
- سرور برای دمو/توسعه است: بدون احراز هویت و rate-limit. پیش از انتشار
  عمومی این‌ها را اضافه کنید.
- تحلیل CPU-bound است؛ سقف کیفیت مهم‌تر از سرعت گرفته شده (فایل ۳۰-۶۰
  دقیقه‌ای ممکن است ده‌ها ثانیه طول بکشد) و پیشرفت زنده نمایش داده می‌شود.
